# v2 모델링 데이터셋

센서 x 10분 단위 하수 고수위 예측 데이터셋. 생성 스크립트는 `scripts/build_dataset.py`.

```powershell
python scripts\build_dataset.py events    # 강우사건·대조 무강우일 정의
python scripts\build_dataset.py sewer     # 사건 창 수위 10분 집계 (원본 7.28GB 스캔)
python scripts\build_dataset.py rain      # 사건 창 강우 10분 정리
python scripts\build_dataset.py features  # 피처·타깃 결합
```

## 산출물

| 파일 | 내용 |
|---|---|
| `event_windows.csv` | 강우사건 22개 + 대조 무강우일 23개의 창 정의 |
| `sewer_10min_event_windows.parquet` | 창 구간 수위 10분 집계, 완전 격자 |
| `rain_10min_event_windows.parquet` | 창 구간 강우 10분, 관측소별·구별 |
| `modeling_dataset_sensor_10min.parquet` | 최종 356,246행 x 61열 |
| `sensor_screening.csv` | 센서별 학습기간 동적범위와 채택 여부 |

## 데이터 계약

**시간 격자.** 서울시 강우 `자료수집 시각`은 `:09 :19 :29 :39 :49 :59` 에 기록된다.
`HH:09` 행을 `[HH:00, HH:10)` 구간의 10분 누적으로 해석하고 `floor("10min")` 으로
수위와 같은 격자에 올린다. 이 해석은 강우-수위 시차상관이 k=0에서 최대(0.241)로
나오는 것으로 검증했다. 규칙을 바꾸면 두 자료가 최대 10분 어긋난다.

**완전 격자.** 원본에는 통신 두절 구간의 행이 아예 없다. 그대로 `shift` 하면
`t+30` 이 실제로는 `t+120` 인 행과 짝지어진다. 창별로 10분 격자를 빠짐없이
되채운 뒤 랙·리드를 만들었고, 관측이 없는 행은 `observed=0` 으로 남겼다.
전체 356,246행 중 관측 333,105행(93.5%).

**사건 경계.** 모든 랙·리드는 `(센서, 사건창)` 안에서만 계산한다. 창 첫 행의
과거 피처와 끝 행의 미래 타깃은 결측이다.

**누출 방지.** 센서별 고수위 임계(p95, p99)는 **학습 사건의 관측행에서만** 계산한다.

## 사건 단위 분할

행 단위 무작위 분할은 쓰지 않는다. `config.py` 의 `TEST_EVENTS`, `VAL_EVENTS` 로 고정.

| 분할 | 사건 | 행 | 센서 |
|---|---|---:|---:|
| train | 38개 (나머지 전부) | 287,473 | 35 |
| val | E17_0904, E11_0731, D0902, D0728 | 37,335 | 33 |
| test | E13_0808, E14_0810, D0818 | 31,438 | 33 |

테스트에 8/8 극한호우(한 관측소 누적 519.5mm)를 둔 것은 의도적이다. 학습에서 본 적 없는
규모의 사건에 모델이 어떻게 반응하는지가 이 프로젝트의 핵심 질문이다.
**이 분할을 바꾸면 이전에 보고한 성능은 전부 무효다.**

## 반드시 알고 시작할 것

지속성 기준선(현재 수위가 그대로 유지된다고 예측)이 매우 강하다.

| 분할 | 예측시간 | MAE | 고수위구간 MAE | p95 분류 F1 |
|---|---|---:|---:|---:|
| test | t+10 | 0.0308 | 0.0880 | 0.952 |
| test | t+30 | 0.0617 | 0.1810 | 0.894 |
| test | t+60 | 0.0874 | 0.2512 | 0.846 |

전체 F1 0.894를 못 넘으면 모델은 의미가 없다. 그런데 이 숫자는 대부분의 행에서
수위가 거의 변하지 않기 때문에 나온 것이고, **정작 중요한 상태 전이는 test 기준
전체의 5.84%(상승 2.97% / 하강 2.86%)뿐**이다. 지속성 기준선은 이 전이를 정의상
100% 틀린다.

따라서 전체 정확도·F1만 보고하면 안 된다. 평가는 `scripts/mareungil/evaluate.py` 를 쓴다.

```powershell
python scripts\run_baselines.py 30
```

대표지표는 **오경보 예산을 고정한 상승전이 재현율** `rise_recall @ stable_low_fpr <= 0.05`.

| 기준선 (test, t+30) | 상승전이 재현율 | 오경보율 | 경보해제율 | 전체 F1 |
|---|---:|---:|---:|---:|
| 지속성 | 0.000 | 0.000 | 0.000 | 0.894 |
| 규칙(강우+상승) | 0.108 | 0.006 | 0.000 | 0.892 |

임계 ±0.05 밴드에 걸친 행은 `AMBIGUOUS` 로 대표지표에서 제외한다(test 24.4%).
분해능이 0.01인데 학습 상승전이의 26%가 임계를 0.01만 넘어 잡음이 섞이기 때문이다.

함께 볼 것: `fall_release_rate`, `onset_catch_rate`와 `median_lead_min`,
고수위 구간 MAE, 센서별 지표(단 마진 적용 후 센서당 RISE가 1~15건뿐이라
개수와 함께 읽을 것), PR-AUC.

"모델이 기준선보다 나쁘다"는 결론이 나왔을 것이다.

## 경보 정책

```powershell
python scripts\run_alarm_policy.py 30
```

**임계값은 고정 확률임계로 확정했다.** 상위 n%·강우량 구간별 등 3종을 시도했고 모두
재현율을 잃었다(`threshold_policy_t30.csv`, `severity_threshold_t30.csv`).

| test t+30 정책 | 오경보율 | 상승전이 재현율 |
|---|---:|---:|
| **고정 확률임계** | 0.029 | **0.648** |
| 상위 n% (센서별) | 0.042 | 0.451 |
| 강우량 구간별 | 0.060 | 0.376 |

오경보율이 사건마다 흔들리는 것은 **결함이 아니라 올바른 동작**이다. 고정임계는
확률이 높은 고강우 구간에 경보를 자동으로 몰아주는데, 상승전이가 몰려 있는 곳이
거기다. 구간마다 오경보율을 똑같이 맞추라고 강제하면 조용한 구간에 예산을 낭비한다.
목표 오경보율을 강제하지 말고 **실현된 오경보율을 재현율과 함께 보고할 것.**

**경보해제는 구조만 해결했다.** 현재 고수위 행만 따로 학습한 해제 전용 모델.

| test t+30 | 상승전이 재현율 | 오경보율 | 경보해제율 | 오해제율 |
|---|---:|---:|---:|---:|
| 해제모델 없음 | 0.648 | 0.029 | 0.000 | 0.000 |
| 해제모델 적용 | 0.648 | 0.029 | **0.418** | 0.117 |

경보를 끌 수 있게 됐고 상승 판정도 손해보지 않았다. 단 **오해제율 0.117**(아직 물이
안 빠졌는데 경보를 꺼버림)이 예산 0.05 를 넘는다. **이 상태로 운영 투입 금지.**

임계 정책을 바꿔 풀 문제가 아니므로(위 결론 참고) 해제 모델 자체의 분별력을 올리거나
연속 n회 하강 확인 같은 보수적 규칙을 넣어야 한다. 설계안 §13.2 참고.
