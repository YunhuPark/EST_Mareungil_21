# 마른길 분단위 해상도 확장 계획

> rev.1 · 2026-08-12 · [MVP 설계서](./마른길_MVP_설계서.md) 8장의 확장 제안
> 이 문서의 모든 수치는 `python scripts/probe_minute_resolution.py`로 재생성한다.

## 1. 한 문장

지역 위험 예측은 지금의 10분 격자로 두고, **개별 센서의 분당 급등을 1분 해상도로 감시하는 트랙을 따로 세운다.**

## 2. 왜 바꾸는가

침수는 "몇 시쯤 위험한가"가 아니라 "지금 이 순간 물이 차오르는가"의 문제다. 현재 파이프라인의 최소 시간 단위는 10분(`config.BIN`)이고, 10분은 보행자가 대피 여부를 판단하기엔 이미 지난 시간이다.

이건 체감이 아니라 실측이다. 2022-08-08 강남·서초 32개 센서 원측정 61,585행에서:

| 관측 사실 | 값 |
|---|---|
| 1분 만의 최대 수위 상승 | **+2.59** (22-0010, 22:54 · 직전 값 0.01 → 2.60) |
| 같은 급의 사례 | 23-0005 +1.84(21:47), 22-0014 +1.51(22:38), 22-0011 +1.23(23:51) |
| 분당 상승 분포 | 중앙값 0.00 / p99 0.09 / p99.9 0.36 |
| 10분 슬롯 내부 진폭이 슬롯 양끝 차이보다 큰 슬롯 | **26.3%** |
| 1분 급등(≥0.20) 171건 중 10분 격자에서 사라지는 것 | **45건 (26.3%)** |

마지막 두 줄이 핵심이다. 10분 격자는 슬롯의 마지막 값만 남기므로, **네 번 중 한 번꼴로 슬롯 안에서 벌어진 급등을 통째로 지운다.** 22:54에 1분 만에 2.59가 오르고 슬롯이 끝나기 전에 빠지면, 현재 모델은 그 순간을 본 적이 없다.

단위가 미확인(설계서 8.4)이라 "2.59가 몇 cm인가"는 아직 말할 수 없다. 하지만 **같은 센서의 분포 안에서 p99.9의 7배**라는 사실은 단위와 무관하게 성립한다.

## 3. 초 단위는 왜 안 되는가

되지 않는다. 원본에 없다.

| 원본 | 명목 | 실측 표본 간격 |
|---|---|---|
| 서울시 하수관로 수위(OA-2527) | "1분" | 60초 89.9% · 120초 9.4% · 180초 이상 0.7% |
| KMA AWS 400·401 분자료 | 1분 | 60초 100% (8/8 구간 2,160행 결측 0) |
| 서울시 강우량 정보(OA-1168) | 10분 | `:09` 계열 10분 |

60초보다 촘촘한 표본은 **단 한 건도 없다.** 그러므로:

- **금지**: 1분 값을 20초로 보간해 "20초 단위 분석"이라고 부르는 것. 없는 정밀도를 만들어내는 것이고, 재난 서비스에서 이건 거짓말이다.
- **대신 한다**: 1분을 하한으로 확정하고, 그 1분 안의 변화 크기를 명시한다. "1분에 p99.9의 7배가 올랐다"는 20초 체감을 뒷받침하는 정직한 표현이다.
- **초 단위가 정말 필요하면** 별도 센싱이 필요하다 — 현장 IoT 수위계, CCTV 영상 기반 수위 추정, 제보 타임스탬프. 전부 이 MVP 범위 밖이며 9장 로드맵에만 둔다.

## 4. 분단위 이득이 있는 곳과 없는 곳

확장 범위를 좁히기 위해 반대 근거도 측정했다.

**이득 없음 — 지역 평균.** 1분 강우와 구별 평균 분당 수위상승의 시차상관은 강남 r≈0(−0.004), 서초 r=0.361(lag 2분)이다. 같은 것을 10분으로 집계하면 서초 r=0.399로 **오히려 더 높다.** 센서를 평균 내는 순간 급등이 서로 상쇄되고, 남는 건 노이즈다.

→ **지역 위험 등급과 30분 주 판단시점은 10분 격자 그대로 둔다.** 설계서 8.1.2의 결정을 뒤집지 않는다.

**이득 있음 — 센서별 급등.** 급등은 특정 센서에서만 터진다(강남 14개, 서초 12개 센서에서 171건). 그리고 1분 강우 5분 누적 첨두가 급등보다 앞선다:

| 구 | 급등 센서 / 건수 | 강우첨두 → 급등 선행시간 |
|---|---|---|
| 강남 | 14개 / 105건 | 중앙값 32분 (p25 7 / p75 60) |
| 서초 | 12개 / 66건 | 중앙값 11분 (p25 3 / p75 45) |

편차가 크다(p25 3분). 그래서 이걸 **예측 리드타임으로 광고하지 않는다.** 다만 "1분 강우가 급등에 선행한다"는 방향성은 확인됐고, 이게 분단위 강우 감시의 근거다.

## 5. 확장 설계

### 5.1 구조 — 대체가 아니라 병행

```
[10분 트랙 · 기존 유지]  10분 격자 → HistGB → 30분 지역 위험 → LOW/HIGH
                                                                  ↓
[1분 트랙 · 신설]  1분 강우 + 1분 수위 → 급등 감시 → SURGE 플래그 → Decision Engine
```

두 트랙은 같은 `asof`를 쓰되 격자가 다르다. 1분 트랙은 **예측이 아니라 감지**다. 이름도 `predict`가 아니라 `surge_watch`로 둔다.

### 5.2 왜 분단위 예측 모델을 만들지 않는가

만들 수 있는 것처럼 보이지만 통계적으로 못 세운다. 8/8 하루 전체의 급등이 171건이고, 사건 단위 3건 홀드아웃(설계서 8.3) 위에서 분단위 이진 분류를 학습하면 유효 표본이 사실상 사건 수만큼밖에 안 된다. 인접 1분 행은 서로 거의 같으므로 행 수는 표본 수가 아니다.

→ M1은 **규칙 기반 감지 + 강우 burst 피처**로 시작한다. 모델화는 M2에서 라벨을 45개 사건 전체로 확보한 뒤에 판단한다.

### 5.3 M0 — 라벨과 데이터 (선행)

| 작업 | 산출물 | 비용 |
|---|---|---|
| 45개 사건 창 전체를 1분 해상도로 추출 | `sewer_1min_event_windows.parquet` | 원본 7.28GB 전량 스캔. 현재 10분 추출과 같은 청크 방식, 집계만 생략 |
| KMA AWS 400·401 분자료 정리 | `rain_1min_event_windows.parquet` | 25MB × 2. 즉시 |
| 급등 라벨 생성 | `surge_labels_1min.parquet` | 센서별 분포 기준(p99.9 배수)으로 정의 |
| 표본 간격·결측 프로파일 | 사건별 60초/120초 비율표 | 8/8은 89.9%/9.4% |

**주의**: 1분 격자도 완전격자로 되채워야 한다. 10분에서 겪은 문제(설계서 8.1, `reindex_full_grid`)가 1분에서는 더 심하다 — 통신두절 구간의 행이 아예 없으므로 그냥 `diff()`하면 **2분 간격 상승을 1분 상승으로 잘못 읽는다.** 위 표의 9.4%가 전부 이 함정이다. `dt == 60`인 표본만 급등 판정에 쓴다(probe 스크립트 `report_minute_rise`와 동일 규칙).

### 5.4 M1 — 급등 감시와 강우 burst

**강우 쪽 (AI 분석 대상).** 1분 강우에서 만드는 피처:

| 피처 | 정의 | 근거 |
|---|---|---|
| `rain_1m_mm` | 직전 1분 강우 | 8/8 최대 강남 2.5(20:42) / 서초 4.0(21:16) |
| `rain_5m_mm` | 5분 이동합 | 8/8 최대 강남 11.5(20:51) / 서초 14.0(21:07) |
| `rain_15m_mm` | 15분 이동합 | 급등 선행 판정의 주 창 |
| `rain_burst_ratio` | `rain_5m_mm / (rain_60m_mm / 12)` | 같은 60분 누적이라도 몰아친 비가 위험하다 |
| `rain_accel` | `rain_5m_mm` 의 5분 변화 | 강해지는 중인지 잦아드는 중인지 |

10분 격자에서는 `rain_burst_ratio`와 `rain_accel`이 정의 자체가 안 된다. **이게 분단위 강우 분석의 실질 산출물이다.**

**수위 쪽.** 센서별 `rise_1m`, `rise_5m`, 그리고 급등 판정. 임계는 센서별 학습기간 분포에서 뽑는다(고정 상수 금지 — 단위 미확인이므로 절대값에 의미가 없다).

**출력.** 센서별 `surge_state ∈ {CALM, RISING, SURGE}`와 감지 시각. 이건 예측 확률이 아니므로 `risk_probability`와 섞지 않는다.

### 5.5 M2 — 계약과 행동 반영

`RiskAssessment`에 블록을 추가한다(설계서 4.3 G0 스키마 갱신 대상에 합류):

```
surge_watch: {
  grid: "1min",
  asof: <ISO8601>,
  sensors: [{ sensor_id, surge_state, rise_1m, detected_at, sample_gap_s }],
  area_surge_count: <정수>,
  rain_burst_ratio: <실수|null>
}
```

행동 정책에는 **TH-05(신설 제안)** 로 넣는다:

> 반경 내 센서에서 `SURGE`가 감지되면, 30분 지역 위험이 `LOW`여도 `MOVE`를 내지 않고 `WAIT`으로 내린다.

근거 우선순위(설계서 2.1)에서 이건 AI 예측이 아니라 **관측 사실**이므로 예측보다 위, 공식정보보다 아래에 둔다. `EVACUATE`는 이 규칙으로 생성하지 않는다 — 하수 급등은 도로 침수 확정이 아니다(8.4).

화면에는 등급이 아니라 사실만 쓴다: "근처 하수 수위가 방금 급격히 올랐습니다". 수치(2.59)는 단위 확인 전까지 표시하지 않는다.

### 5.6 재생 클럭

현재 데모는 10분 tick 재생이다. 1분 트랙을 보이려면 재생 클럭을 1분으로 내려야 한다. 10분 예측은 10 tick마다 갱신, 급등 감시는 매 tick 갱신이다. 이건 UI·서비스 작업이므로 `services/`, `web/` 구현이 선 필요하다(현재 미구현).

## 6. 합격 기준

| 항목 | 기준 |
|---|---|
| M0 | 45개 사건 1분 완전격자 생성, 중복 키 0건, 사건별 60초 표본 비율 기록 |
| M0 | 8/8 구간에서 이 문서의 5개 수치가 재현 |
| M1 | 10분 격자가 놓치던 급등 45건 중 **40건 이상을 1분 트랙이 감지** |
| M1 | 무강우 대조 사건 23건에서 `SURGE` 오탐 사건당 1건 이하 |
| M1 | 급등 감지 지연 ≤ 2분 (감지 시각 − 실제 급등 시각) |
| M2 | `surge_watch` 블록이 스키마 검증 통과, 픽스처 5종에 반영 |
| M2 | 추론 예산 유지 — 1분 트랙 포함 50ms 이하(N-01) |

## 7. 하지 않는 것

- 1분 값을 초 단위로 보간하지 않는다.
- 30분 주 판단시점과 지역 위험 등급 산출을 바꾸지 않는다. 보고된 성능(재현율 0.648 / 오경보 0.029 / 사전감지 85.3%)은 10분 트랙의 것이며 이 확장으로 갱신되지 않는다.
- 급등 감지를 "예측"이라고 부르지 않는다. 이미 일어난 일의 관측이다.
- 급등으로 `SEVERE`나 `EVACUATE`를 생성하지 않는다.
- 하수관 급등을 도로 침수로 단정하지 않는다.
- 급등 수치를 cm·%로 화면에 쓰지 않는다(단위 미확인).

## 8. 위험

| 위험 | 영향 | 대응 |
|---|---|---|
| 1분 원본 전량 스캔 비용 | M0가 길어짐 | 사건 창만 추출. 현재 10분 파이프라인과 같은 청크 경로 재사용 |
| 통신두절 2분 간격을 1분 상승으로 오독 | 급등 과대 계상 | `dt == 60` 표본만 판정. 9.4%가 여기 걸린다 |
| 급등 오탐으로 `WAIT` 남발 | 서비스가 아무 데도 못 가게 함 | 무강우 대조 23건으로 오탐 예산 검증(6장) |
| 단위 미확인 지속 | 임계 절대값 불가 | 센서별 분포 기준 유지. 물순환안전국 회신 시 재보정 |
| MVP 동결 일정 침범 | G2 지연 | 이 트랙은 **G2 이후 별도 브랜치**. MVP 데모 경로에 넣지 않는다 |

## 9. 로드맵 (범위 밖)

초 단위 관측이 실제로 필요하다면 필요한 것은 알고리즘이 아니라 센서다 — 현장 IoT 수위계, CCTV 영상 기반 수위 추정, 지하공간 유입 감지. 지자체 협의 사안이며 현재 데이터로는 대체할 수 없다.
