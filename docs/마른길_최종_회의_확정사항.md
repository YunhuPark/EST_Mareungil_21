# 마른길 최종 회의 확정사항

윤지님 제출용 최종 결정 정리본입니다.

## [확정] 안건사항 1

**안건사항:** 각자 만든 AI·결정엔진·경로·화면이 실제 앱 안에서 처음부터 끝까지 연결돼 돌아가는 건가요? 중간에 사람이 값을 복사하거나 미리 정한 화면만 보여주는 구간은 어디인가요?

**확정 내용:**

하나의 사용자 요청이 AI 예측, 행동 판단, 필요한 경우 경로 탐색, 최종 행동, 화면 표시까지 사람의 개입 없이 자동으로 연결되는 것을 E2E 완료 기준으로 한다. Mock API와 시연용 고정값은 실제 연동 구간과 구분하고, 동일한 scenario_id를 통해 각 모듈의 입력·출력을 추적한다.

## [확정] 안건사항 4

**안건사항:** 센서 여러 개의 위험확률을 골목이나 지역 하나의 위험도로 어떻게 합쳤나요? A센서 50과 B센서 50이 같은 위험이 아닐 수 있는데 어떤 기준으로 결합했나요?

**확정 내용:**

현재는 강남역 반경 1km의 센서 5개에 동일한 가중치를 적용하고, 각 센서의 30분 후 위험확률이 0.33 이상이면 위험표 1개, 전체 센서 중 위험표 비율이 0.5 이상이면 지역 HIGH로 계산합니다. 이 방식은 센서 거리·배수구역을 반영하지 않고 0.34와 0.99도 동일하게 처리하므로 골목·도로 단위 위험도로 검증되지 않았습니다.

검증되지 않은 거리·확률 가중치를 임의로 추가하지 않으며, 최종 통합 전까지 결합방식의 검증 근거를 확보하지 못하면 area_risk를 행동판단·경로계산·UI에서 제거합니다. 제거 시 LOW가 아니라 null 또는 UNKNOWN으로 처리하고, 개별 센서 예측값은 참고정보로만 유지합니다. 특정 도로의 경로 제외는 공식 통제와 확인 침수정보에만 적용합니다.

## [회의 후 확정완료] 안건사항 8

**안건사항:** 예측 생성시각과 마지막 데이터 갱신시각은 무슨 뜻인가요? 데이터를 몇 분 못 불러오면 오래된 정보 또는 판단불가로 볼지, 왜 시간이 지났다고 무조건 WAIT로 바꾸면 위험한지 정했나요?

**확정 내용:**

응답에는 관측시각, 예측 생성시각, 예측 대상시각, 마지막 데이터 갱신시각과 데이터 경과시간을 함께 표시합니다.

- **10분 초과:** 현재 행동을 유지하고 마지막 데이터와 ‘갱신 지연’을 표시합니다.
- **30분 초과:** 해당 데이터를 판단 근거에서 제외합니다.
- **20분 단계:** 별도의 상태나 행동 전환 기준으로 사용하지 않고 10분·30분 기준으로 단순화합니다.

30분을 초과해도 무조건 WAIT로 바꾸지는 않습니다. 다른 직접적인 안전 신호가 없을 때만 MOVE → WAIT로 전환합니다.

- 실제 고립 확인 → EMERGENCY
- 지하 물 유입·하수 역류·계단 물 유입 → EVACUATE
- 공식 대피지시 → EVACUATE

경로 응답에도 기준시각과 데이터 상태를 전달합니다. 공식 통제정보나 공간자료가 누락·단절되어 경로 안전성을 판단할 수 없으면 DATA_UNAVAILABLE, no_safe_route=null을 반환하며, 최종 행동은 결정엔진이 위 우선순위에 따라 판단합니다.

## [회의 후 확정완료] 안건사항 15

**안건사항:** 대피해야 한다는 결과가 나왔는데 열린 대피시설도 없고 안전경로도 없거나 데이터까지 못 불러오면 사용자는 어디로 가야 하나요?

**확정 내용:**

팀원 전원 의견에 따라, EVACUATE 이후 시설·경로·데이터 문제가 발생하더라도 자동으로 EMERGENCY로 변경하지 않고 EVACUATE를 유지합니다. 임의 경로는 생성하지 않으며, 다음과 같이 실패 원인을 구분해 안내하고 119 버튼을 강조합니다.

- NO_SAFE_POINT: 안내 가능한 안전거점 없음
- NO_SAFE_ROUTE: 안전거점은 있으나 허용 가능한 경로 없음
- DATA_UNAVAILABLE: 데이터 부족으로 경로 존재 여부를 판단할 수 없음

사용자가 실제 고립 상태를 신고한 경우에만 기존 우선순위에 따라 EMERGENCY로 전환합니다.

## [회의 후 확정완료] 안건사항 16

**안건사항:** 목적지가 통제됐거나 실외에서 안전한 경로를 찾지 못했을 때 그냥 WAIT라고 하면 도로 한가운데 멈출 수 있는데, 이때 어떤 행동을 안내하나요?

**확정 내용:**

목적지 차단과 안전경로 없음은 서로 다른 상태로 구분하며, 두 경우를 모두 단순 WAIT로 처리하지 않습니다.

- DESTINATION_BLOCKED: 공식 통제 또는 확인된 침수정보에 목적지가 명시적으로 포함된 상태입니다. 좌표 거리만으로 차단을 추정하지 않으며, route_attempted=false, no_safe_route=null을 반환합니다. 현재 처리상 MOVE를 유지하더라도 기존 목적지로 계속 이동하라는 뜻은 아닙니다. 기존 경로안내를 중단하고 **“현재 목적지는 이용할 수 없습니다. 다른 목적지를 선택해 주세요.”**라고 안내합니다. 새 목적지가 입력되면 결정엔진이 행동을 다시 판단합니다.
- NO_SAFE_ROUTE: 목적지는 유효하지만 경로 탐색 후 허용 가능한 후보가 없는 상태입니다. route_attempted=true, no_safe_route=true를 반환하고, 확정된 후처리 규칙에 따라 MOVE → WAIT로 전환합니다. **“안전이 확인되지 않은 경로로 이동하지 마세요.”**라고 안내하며, 현재 위치가 위험하다면 주변에서 위험 노출을 줄일 수 있는 장소를 우선 확인하도록 추가 안내합니다.

실제 고립이 확인되면 위 규칙보다 우선하여 EMERGENCY로 전환합니다. UI에서도 목적지 이용 불가와 안내 가능한 안전경로 없음을 서로 다른 상태와 문구로 표시합니다.

## [확정] 안건사항 17

**안건사항:** WAIT가 나온 뒤 몇 분 뒤 상황이 좋아지면 다시 MOVE로 바뀌나요? 잠깐 수치가 낮아진 것만 보고 움직이지 않도록 복귀 규칙을 정했나요?

**확정 내용:**

현재 MVP에서는 위험값이 낮아졌다는 이유만으로 WAIT → MOVE로 자동 복귀하지 않는다. 재판정 요청에서 결정엔진이 MOVE를 다시 확정한 경우에만 경로엔진을 호출. 자동 복귀 조건은 후속 검증 대상으로 분리한다.

## [회의 후 확정완료] 안건사항 18

**안건사항:** 사용자가 이동 중 갑자기 비가 많이 오거나 도로통제·대피소 만석이 생기면 앱이 언제 행동과 우회경로를 다시 계산하나요? MVP에서는 어떤 방식으로 이 변화를 시연하나요?

**확정 내용:**

투표 결과 5명 전원 동의로, 자동 이벤트 방식이 아닌 **구현 과정에서 오류가 가장 적은 수동 버튼 방식**으로 재판단을 실행합니다. 버튼을 누르면 2022년 리플레이 시각을 변경하고, 해당 시점의 AI 예측·공식정보·데이터 상태·사용자 상태를 다시 불러와 결정엔진을 실행합니다.

재판단 결과가 WAIT, EMERGENCY, UNAVAILABLE이면 기존 경로안내를 중단하고, MOVE 또는 EVACUATE이면 변경된 조건으로 경로 후보를 다시 평가합니다. 버튼의 위치·명칭·조작 주체는 구현 안정성을 확인한 후 정합니다. 실시간 외부 API·사용자 위치·통제·대피시설 변화를 자동 감지해 재탐색하는 기능은 MVP에서 제외합니다.

## [회의 후 확정완료] 안건사항 19

**안건사항:** 완전히 고립된 뒤 119를 안내하는 것보다, 안전한 선택지가 사라지기 전에 조금이라도 빨리 판단해서 대피시키는 기능을 구현할 수 있나요?

**확정 내용:**

조기고립 예측은 현재 도로정보와 정답 라벨이 부족하므로 MVP에서 제외하고 후속 연구로 분리합니다. 이번 MVP에서는 사용자가 실제 고립 상태를 신고한 경우 trapped=true → EMERGENCY 규칙만 적용합니다.

후속 연구에서는 시간에 따른 공식 통제·확인 침수구간·대피경로 변화·시설 이용 가능 상태와 실제 고립 여부 정답 데이터를 확보해 별도로 검증합니다. 이를 바탕으로 고립 위험도, 남아 있는 이동 가능 후보 수, 후보 감소 추세, 고립 예상시간과 대피 가능시간을 산출하는 방향으로 확장합니다.

## [확정] 안건사항 24

**안건사항:** 재난 중 대피시설이 대기·개방·혼잡·만석·폐쇄·침수·접근차단으로 계속 바뀌는데 누가 언제 갱신하나요? 당장 실시간 연동이 어렵다면 MVP에서는 어떻게 처리하나요?

확인되지 않은 상태는 UNKNOWN으로 유지하고 임의로 OPEN 처리하지 않는다. 데모 상태값을 쓴다면 실제 데이터와 분리된 MOCK/DEMO_FIXTURE로 표시한다.

## [확정] 안건사항 28

**안건사항:** 침수 때 이용자가 몰려 서버가 느려지거나 터지면 위급한 사용자부터 처리할 수 있나요? 119 안내와 긴급요청을 일반 기능과 분리한 전용 처리 구조가 가능한가요?

**확정 내용:**

EMERGENCY 판단과 119 안내를 경로엔진과 분리하고 경로 계산보다 우선 처리한다. 경로 후보 비교 실패 시 임의 경로를 생성하지 않고 DATA_UNAVAILABLE과 제한된 지도정보를 제공한다. MVP에서는 별도의 긴급 전용 서버는 구축하지 않으며, 경로 장애 시에도 긴급기능과 기본 행동안내가 유지되도록 한다.

## [확정] 안건사항 29

**안건사항:** 재난 전용앱은 평소 잘 쓰지 않는데 독립앱, 지도·내비 기능 연동, 지자체 API, B2G 시스템 중 어떤 형태로 상용화하는 것이 가장 현실적인가요?

**확정 내용:**

B2G 시스템을 본체로 하고, 시민 서비스는 기존 지도·지자체 앱에 API형태로 연동하는 방향을 우선한다. 현재 경로 결과는 안전보장 내비게이션이 아닌 대피경로 후보 비교로 한정한다

## [회의 후 확정완료] 안건사항 32

**안건사항:** 특정 대피소가 만석이거나 갑자기 문을 닫고, 2순위·3순위까지 갈 수 없으면 바로 다음 후보를 어떻게 찾나요? 후보가 하나도 남지 않았을 때는 무엇을 안내하나요?

**확정 내용:**

대피시설의 FULL(만석), CLOSED(폐쇄), UNAVAILABLE(접근 불가) 상태가 확인되면 해당 시설을 즉시 후보에서 제외합니다. 미리 계산한 후보 목록에서 2순위·3순위의 운영상태, 수용 가능 여부와 경로 안전성을 다시 확인한 뒤 조건을 충족하는 다음 후보로 전환합니다.

조건을 충족하는 후보가 하나도 남지 않으면 무한 재검색이나 임의 목적지 생성을 하지 않고 NO_SAFE_POINT를 반환합니다. 이때 기존 합의대로 EVACUATE는 유지하고, ‘안내 가능한 안전거점 없음’을 표시하며 119 버튼을 강조합니다. 실제 고립이 확인된 경우에만 EMERGENCY로 전환합니다.

MVP에서는 실시간 시설상태 연동으로 표현하지 않고, 1순위 FULL → 2순위 전환 → 후보 0개 → NO_SAFE_POINT 흐름을 고정 픽스처로 시연합니다.

## [회의 후 확정완료] 안건사항 33

**안건사항:** 서버와 AI·결정·경로·UI 중 하나가 고장 나면 누가 알아차리고 대응하나요? 배포·로그·모니터링·장애처리 담당을 정했나요?

**확정 내용:**

별도 서버 배포 없이 로컬 환경에서 시연합니다. 전체 앱의 통합·실행 및 개발 세션 종료 후 정상 작동 확인은 윤지님이 담당합니다. 모듈별 오류 확인은 기존 역할에 따라 윤지님은 AI, 진희님은 결정엔진, 윤후님은 경로엔진, 예지님은 UI를 담당합니다.

경로 모듈은 계약 테스트·고정 픽스처·응답시간·오류로그로 정상 여부를 확인하고, 장애 시 status, scenario_id, 데이터·정책 버전을 기록합니다. 경로 오류에는 DATA_UNAVAILABLE을 반환한 뒤 결정엔진과 UI의 백업안내가 작동하는 순서로 확인합니다.

## [확정] 안건사항 34

**안건사항:** 골목 단위 실시간 데이터, 공식 통제, 대피시설 상태를 지자체·담당부서와 협약해 받을 수 있나요? 누가 제공·갱신·정정하고 책임지는지 현실적으로 정할 수 있나요?

**확정 내용:**

MVP는 과거 픽스처라고 명시. 상용화에는 공식통제, 상용화에는 공식 통제·확인 침수·대피시설 상태별 제공기관, 갱신자, TTL, 정정 책임과 장애 연락체계를 별도 표로 확정할 것,운영 주체가 없는 데이터는 완전 차단 근거로 사용 하지 않는다.

## [회의 후 확정완료] 안건사항 35

**안건사항:** 판단 중 에러, 네트워크 끊김, 서버 과부하가 생기면 시연과 실제 서비스가 각각 어떻게 버티나요? 실패했을 때 보여줄 백업화면과 복구 순서를 연습했나요?

**확정 내용:**

AI와 공식정보는 분리합니다. AI 장애가 발생해도 공식 통제정보와 사용자 상태처럼 독립적으로 확인 가능한 정보로 결정엔진의 판단을 계속하며, 정보가 부족하면 임의 판단 대신 DATA_UNAVAILABLE을 반환합니다. 공식 통제도로는 AI 상태와 관계없이 경로 후보에서 제외합니다.

경로 API가 실패하면 임의 경로나 가상 선을 생성하지 않고 오류 상태와 한계를 표시합니다. 네트워크·경로 장애 중에도 119 버튼과 기본 행동카드는 유지합니다.

MVP 통합 후 다음 세 가지 장애 리허설을 각각 1회 진행합니다.

- 네트워크 OFF → 백업화면 → 복구
- AI timeout → 공식정보·사용자 상태 기반 판단 또는 DATA_UNAVAILABLE
- 경로 API 실패 → 경로 중단·대체안내

장애 발생시각부터 감지, 백업 전환, 사용자 안내, 정상 복구까지 로그로 남깁니다. 정상 후보·DESTINATION_BLOCKED·NO_SAFE_ROUTE·DATA_UNAVAILABLE 고정 픽스처도 준비합니다. 담당은 기존 역할에 따라 윤지님은 AI·통합, 진희님은 결정엔진 백업판단, 윤후님은 경로 오류, 예지님은 백업화면을 확인합니다.

## [확정] 안건사항 36

**안건사항:** 2022년 과거상황을 시연할 때 당시 재난문자·공식 통제·확인 침수정보도 실제 발령시각에 맞춰 함께 재생하나요?

**확정 내용:**

2022년 과거상황 시연에서는 당시 사용자가 실제로 알 수 있었던 정보만 해당 재생시각부터 적용한다.

공식 통제정보와 확인 침수정보에는 실제 발생·관측시각인 event_time과 시스템 또는 시민에게 공개된 시각인 available_time을 구분해 기록한다. 시연시각보다 available_time이 빠르거나 같은 정보만 AI·결정·경로 판단에 사용하며, 이후에 공개된 정보는 미리 사용하지 않는다.

공식 통제와 확인 침수정보는 발령·관측·공개시각이 확인된 경우에만 해당 시점부터 경로 제외 근거로 사용한다. 침수흔적도는 정확한 발생시각을 나타내는 자료가 아니므로 특정 시각의 도로 차단 근거로 사용하지 않고, 위험 가중치와 대피경로 후보 비교를 위한 정적 참고자료로만 활용한다.

출처·발생시각·공개시각을 확인할 수 없는 정보는 null로 처리하고 가상 공식정보로 채우지 않는다. 시연용으로 만든 값이 필요한 경우에는 실제 정보와 구분해 DEMO_FIXTURE로 표시한다.

## [확정] 안건사항 37

**안건사항:** 고령자·아이동반자에게 더 긴 시간여유, 짧은 우회거리, 완만한 경사를 준다면 정확히 어떤 수치로 적용하고 왜 그 수치를 골랐나요?

**확정 내용:**

고령자·아이동반 프로필은 기획서와 발표 범위에 포함된 핵심 사용자 유형이므로 MVP에 유지합니다. 기존에 설정한 60분·30분 기준, 우회상한 1.15, 경사가중치 1.5를 MVP 정책값으로 우선 적용하고, 개발·검증 과정에서 더 적절한 값이 확인되면 수정합니다.

사용자 유형에 따라 안전 기준이나 위험구간 제외 기준을 완화하지 않습니다. 동일하게 안전성이 허용된 후보 안에서만 고령자·아이동반자에게 적합한 경로와 시설의 우선순위를 조정합니다.

## [회의 후 확정완료] 안건사항 39

**안건사항:** 하수 고수위나 위험확률이 경계 근처에서 오르내릴 때 MOVE와 WAIT가 계속 바뀌지 않게 했나요? 위험 진입과 해제 기준을 다르게 두었나요?

**확정 내용:**

현재 MVP에서는 윤지님의 예측 AI 단계에서 검증한 위험값 진동 완화만 적용합니다. 결정엔진에는 위험 하락에 따른 WAIT → MOVE 자동복귀와 별도의 행동 해제 임계값·유지시간을 적용하지 않습니다. 따라서 근거와 검증이 없는 70·50·30초 예시값은 사용하지 않습니다.

경로엔진은 행동 전환 규칙을 임의로 추가하지 않고, 동일한 입력과 버전에는 동일한 결과가 나오도록 동점 후보의 정렬 기준만 고정합니다. 문서에는 AI 예측값의 진동 완화와 서비스 행동의 자동복귀가 서로 다른 기능임을 명확히 구분합니다.

행동 자동복귀는 향후 데이터 갱신주기, 연속 정상시간, 공식 통제 해제 및 현장 위험징후 해소 조건을 검증한 후 도입합니다.
